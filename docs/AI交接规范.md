# 103 工作区与 AI 交接规范

固定入口：`/home/tina/OmniRackWorkspace/START-HERE.md`。本规范的目标是使继任 AI 不依赖上一位 AI 的本地文件、会话记忆或环境。服务器文件中不得保存 SSH 密码；接入凭据通过受控渠道提供。

## 接班第一轮

以下命令直接在 103 上执行，不要求任何本地仓库：

```sh
cd /home/tina/OmniRackWorkspace
cat START-HERE.md AGENTS.md
cat handoffs/latest/HANDOFF.json
bin/omni status
. toolchains/env.sh
```

若尚无 `latest`，以入口列出的初始化记录为准。先核对工作树、Git HEAD、脏文件、运行发布记录及待完成项，再采信交接结论。复核原包/源码/镜像的摘要，不把文件名等同于真实性。若用户最新目标与旧交接冲突，记录调整后继续执行当前目标。

`omni status` 只读取 Git 和任务文件，并显示发布指针；**它不验证 Docker 容器是否真的运行该版本**。容器、端口、健康和镜像 ID 还须用发布管理器状态与实际只读命令核实。

## 建立任务与所有权

```sh
bin/omni task-new api-order-sync --actor 'AI-名称/会话标识' --goal '补齐对接接口并验证权限与幂等'
cd worktrees/api-order-sync
```

任务 ID 使用 3–64 位小写字母、数字、连字符，首位为字母。工具在规范仓库当前 HEAD 创建 `work/api-order-sync` 分支并写入任务文件。创建操作有文件锁；同名任务或同名工作树存在时拒绝覆盖。创建中途失败会保留 `provisioning-failed` 状态供检查，不自动清理可能有价值的现场。

接手已有任务应使用该任务已有工作树和分支，先看状态，联系/确认前任已停止写入，然后显式记录接手人。不能因为会话结束或时间过去就断言前任的工作无效。工具锁只串行化元数据操作，并不阻止其他进程直接编辑源码；实际单写入者纪律仍然必要。

并行子任务要划定文件所有权；共享文件的修改顺序须由主任务协调。合并前先保留各自提交，核查相互影响，随后重新执行适用验证。不要把尚未合并、尚未测试的分支称为规范版本。

## 开发记录与证据

每个测试结果至少记录：命令、工作目录、提交/源码摘要、工具版本、执行时间、退出状态、结果文件路径和验证范围。失败日志应保留；修复后注明新的成功结果，不能删除失败证据制造“全绿”。

API、事务和安全变更应覆盖真实行为：旧令牌失效、权限更新、并发冲突、幂等参数不一致、数据库错误和超时，而不只是匹配实现细节。真实 LDAP、SMTP、扫码摄像头、容量与高可用性未验证时必须明确写出。依赖扫描通过仅表示扫描工具与数据库覆盖范围内的结果。

机密配置不复制进 Git 或交接包。工作区、交接包和备份设为私有权限。已忽略文件不会进入未跟踪快照，标准名称的 `.env`、密钥等会排除；任意源文件、命令或正文中的秘密仍需人工检查。测试账号与一次性口令不应写入公开报告。

## 交班步骤

先停止该工作树内的写操作，保存必要改动，并把日志放入 `evidence/<task-id>/`。优先提交可解释的源码变化；未完成变化可以保留，但不能假装已提交。

```sh
bin/omni handoff api-order-sync \
  --status handoff \
  --summary '已实现订单映射；并发回归失败，尚未发布' \
  --next '在本工作树修复冲突重试，再执行记录中的集成命令' \
  --check 'go test ./...：退出 1，见 evidence/api-order-sync/go-test.log' \
  --evidence evidence/api-order-sync/go-test.log \
  --risk '外部系统未提供测试凭据，端到端对接未验证'
```

`--check`、`--evidence`、`--risk` 可重复。证据路径必须是工作区内的现存普通文件；工具记录 SHA-256。`--check` 是操作者声明，工具不会自动执行该命令；继任者必须结合原始日志复核。`--next` 应给出确定的下一步，不写泛泛的“继续优化”。

状态使用：

- `handoff`：工作仍在进行，已准备让继任者继续。
- `needs-input`：明确缺少哪项用户/外部信息，仍应说明可以独立完成的工作。
- `complete`：任务验收条件已满足，明确部署与否、风险和验证边界；不把“本轮结束”写成“任务完成”。

工具输出一个不可覆盖的快照目录，含：

| 文件 | 内容 |
| --- | --- |
| `HANDOFF.json` | 结构化交接主记录；实际 Git 分支、提交、状态、目标、声明、下一步、风险、证据摘要 |
| `working-tree.patch` | 相对 HEAD 的已暂存和未暂存改动合并快照，包含二进制补丁；敏感路径排除 |
| `untracked.tar.gz` | 未跟踪且未忽略的普通文件，敏感路径排除 |
| `README.md` | 简短阅读入口 |

`HANDOFF.json` 的 `schema_version` 为 1。`snapshot_sha256` 校验补丁和未跟踪包；`evidence` 中逐项给出服务器路径和摘要；`excluded_secret_paths` 明示未保存的敏感路径。存在此类改动时工具拒绝 `complete`，要求先单独安全保全并厘清状态。大于 32 MiB 的未跟踪文件和符号链接会拒绝打包，应移入有明确用途的证据区或先处理，再重试。

快照是辅助恢复材料，不能代替 Git 提交。恢复前先核查版本、校验和、包成员和当前工作树，检查 `git apply --check`，在新隔离工作树试用；不自动应用、不覆盖现有文件。交接不会删除原工作树，也不会执行 reset、clean、强制检出或数据库恢复。

## 交接内容验收

继任者必须能仅靠 103 回答：用户的最终目标是什么；哪些端口/数据不可动；实际基线和当前提交是什么；还有哪些脏文件；哪些检查真的运行并通过/失败；哪些功能只做了静态推断；生产/验证实例目前在哪个版本；下一步精确命令是什么；哪些外部依赖或风险仍未解决。

若其中任何一项缺失，补写记录后继续可独立完成的工作。不要依赖聊天里的“已完成”“源码完整”“绝对安全”等无证据结论。对安全性和完整度采用可核实的检查项与范围说明，不承诺没有任何隐藏缺陷。
