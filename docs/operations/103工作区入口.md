## 接手顺序

1. `cat /home/tina/OmniRackWorkspace/AGENTS.md` 和本文件。
2. `. /home/tina/OmniRackWorkspace/env.sh`，执行 `omni status`；查看 `handoffs/latest`。先核对 Git、容器和当前发布身份，再采信历史交接中的结论。
3. 阅读 `docs/代码评估与风险登记.md`、`docs/架构与集成规范.md` 和任务相关接口。识别未提交工作与尚未验证项。
4. `omni task-new TASK --actor AI_NAME --goal '具体目标'`，进入命令返回的独立 worktree。不得覆盖其他 AI 的工作。
5. 在该 worktree 完成修改、针对性测试、接口生成和评审，将原始证据写入 `evidence/TASK/`，按照 `docs/AI交接规范.md`交接。

以上命令中的 TASK 使用小写字母、数字和连字符，且每个任务唯一。`omni --help` 是当前真实 CLI 的权威用法。首次维护接续本轮 hardening 的工作树和任务时，先读 latest，避免再创建平行版本。

Go/Node 二进制从官方发布下载并校验。依赖缓存及 Docker 镜像是可重建缓存；`package-lock.json`、`go.sum`、工具版本及结果才是可追溯依据。Go1.27.3 用于本轮维护；历史1.24.13结果只能作为当时比较证据。

`nas-check.sh` 使用专属临时 PostgreSQL 16 容器，不接受业务库 URL。它运行 Go 测试、前端测试与构建、契约检查、真实数据库并发不变量和 HTTP 回归。LDAP/SMTP/摄像头等外部设备并未因此得到验证；UI 浏览器回归是另一条显式命令，见脚本帮助和当次证据。

## 发布与恢复

先构建可审阅的版本，完成备份实际恢复演练和新旧迁移兼容性验证，再使用 Git 管理的 `scripts/nas-release.py`。`status`/`validate` 为检查；`activate` 才会变更15174应用。发布全程持有互斥锁，使用不可变版本、镜像 ID、秘密配置快照和证据摘要，禁止 `latest`、就地覆盖镜像标签和直接在旧 release 中改文件。

历史 rea.1 的控制器保留用于溯源，已发现它们有路径/锁和失败状态缺陷；**它们不是今后的受支持发布入口**。新控制器要求 schema_version=2 和兼容的上一版记录。历史版本若要纳入自动回滚，必须新建“收编基线”版本并记录同一运行镜像、配置摘要和核验结果，不能修改原有历史来补写“已验证”。

应用回滚不等于数据库降级。禁止自动恢复生产数据库或运行 `compose down -v`。数据库恢复必须经过明确授权、停止写入和完整恢复步骤；测试恢复在独立临时数据库进行。新增破坏性迁移前，必须设计兼容窗口并明确数据回退方式。
