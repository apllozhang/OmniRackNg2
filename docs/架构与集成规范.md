# 架构、API 与业务系统集成规范

评估基准：本仓库实际源码与 Gin 注册表，2026-10-28。本文件区分已存在的能力、已确认的限制和后续设计；没有把计划写成已实现功能。运行版本、镜像摘要和 103 部署验证以`/home/tina/OmniRackReplica-releases/` 中当次发布记录为准。

## 1. 适用结论

此系统可以作为内部机柜、设备与资产运营系统继续开发。现有分层、PostgreSQL 事务、资源版本、U 位排斥约束及审计记录是可沿用的基础。它目前仍是面向单组织、有限规模、第一方网页的应用，不能仅因有 `/api/v1` 和 JWT 就当作成熟的企业集成平台。

反编译符号、路由及原包文件匹配只能证明相应证据的吻合，不能证明全部业务语义、异常分支、授权边界与原系统完全一致。每次二次开发应记录采用的业务规则及回归证据；已修复的原有行为也不应为了“复刻一致”恢复成缺陷。

## 2. 当前边界和职责

| 层 | 当前实现 | 评估与约束 |
|---|---|---|
| 网页与入口 | 前端静态站点、Nginx 代理 `/api/` 和 `/health/` | 第一方同源应用；跨域、统一网关、证书与外部身份接入并未因此自动具备 |
| HTTP | `internal/router`、`internal/handler`、`internal/response` | Gin 注册路由；通常返回 SUCCESS/错误信封；资产导出返回原始 JSON |
| 业务 | `internal/service` | 资源、设备位置、审批、库存流转、盘点、终端交接、通知；部分业务已抽象 Store 接口 |
| 数据 | `internal/repository`、`internal/model` | PostgreSQL + GORM；UUID、软删除、version、事务与审计；部分资产 handler 仍直接操作 DB |
| 后台任务 | `cmd/server/main.go` | 进程内循环刷新提醒、分发通知；没有独立任务平台、通用业务事件队列或死信队列 |
| 交付 | Compose、镜像、构建身份、发布与回滚记录 | 必须将源码 commit、配置摘要、镜像摘要、迁移与证据作为一次发布关联保存 |

资源与设备的 handler/service/store 分层更完整；`asset_operations_handler.go` 内还包含盘点发现、提醒确认、最低库存、查询、导出和审计的 SQL/事务。以后新增规则应落在 service，用 Store/Repository 屏蔽持久化；逐项迁移这些旧逻辑，避免形成第二套规则。

## 3. API 的唯一契约入口

- `backend/api/openapi.yaml`：完整 OpenAPI 3.0.3，采用 JSON 文法保存（兼容 YAML 1.2），覆盖实际 **122 个 method/path、89 个路径、83 个被引用的数据 schema**。
- `docs/api-接口清单.md`：逐接口方法、原始 Gin 路径、handler、源码位置、请求体、query 及权限策略。
- `docs/api-错误码清单.md`：从 handler / middleware / router 中静态定义抽取的错误码与位置；它不是“所有接口都返回所有错误”的列表。
- `backend/api/openapi.legacy.yaml.txt`：原始历史文档，仅用于追溯。它有断行导致的 YAML 语法错误、遗漏路由和过期声明，不得再作为活跃契约。

契约由实际注册表和 Go AST 生成，响应类型映射由人工核对 handler 返回值。没有从路由名称猜测请求字段，也没有把数据库 `not null` 当作 HTTP 必填验证。`ShouldBindJSON` 接收的模型字段不等于可写字段：关联对象、ID、创建时间、version 等最终以服务赋值和白名单为准。当前结构契约不是完整的业务规则验证器；集成前仍要完成具体操作的业务验收。

在 **103 工作区仓库根目录**运行（不依赖任何 Mac 本地文件）：

```sh
python3 scripts/api-contract.py --check
cd backend
go test ./cmd/route-inventory
go run ./cmd/route-inventory
```

更新接口后，在根目录执行 `python3 scripts/api-contract.py` 重新生成三个活跃契约文件，审阅差异，再执行 `--check`。如需指定 Go 路径，设置 `GO_BIN=/path/to/go`。默认脚本只需要 Python 标准库及仓库现有 Go 依赖；首次编译若没有模块缓存，Go 工具链仍可能下载依赖。它不会连接业务 DB、启动 worker、监听端口或访问运行实例；`--check` 不改写契约文件，Go 编译缓存仍由工具链管理。

命令遇到未经评审的新 handler 会失败，要求补齐响应类型映射。它验证注册路由、路径参数、operationId 唯一性、schema 引用以及文件是否漂移。它不验证真实数据、外部通知可达性、全部业务分支或代理配置；新接口仍需相应 HTTP/业务集成测试。

## 4. HTTP、错误、并发与重试

| 主题 | 当前事实 | 客户端约定 |
|---|---|---|
| 版本 | 活跃业务路径为 `/api/v1`；健康检查在 `/health` | 不使用 SPA 页面地址当作 API；将服务 base URL 外置配置 |
| 成功 | `code: SUCCESS`，通常 HTTP 200，创建通常 201 | 同时读取 HTTP、code 和 data；审批相关动作可能 `executed=false`、返回审批记录 |
| 错误 | `code`、`message`，可选 `details`、`requestId` | 以状态与 code 分支，message 仅用于展示；框架 panic/代理失败可能不是该信封 |
| 关联 | `X-Request-ID` 与 JSON 的 requestId；后端校验长度和字符集 | 保存响应 ID 关联日志；Nginx 可以重写调用方传入的 ID，不把它当成幂等键 |
| 鉴权 | Bearer JWT；运行路由必须接入实时账号与 version 验证 | 删除/停用/变更账号及撤销后旧 token 不再有效；401 重新认证；503 AUTH_UNAVAILABLE 保留凭证、退避重试 |
| 注销 | 递增账号 version，撤销该账号全部会话 | 清理本地 token；会同时影响同账号其他客户端，不能把一个共享账号作为多个集成的长期身份 |
| 乐观并发 | 多数更新/删除要求 version；位置因接口而异 | 先读取当前 version，原样提交；409 后重读、合并或交由人工决定，禁止自动覆盖 |
| 幂等 | 无通用 `Idempotency-Key`；部分库存请求有 submissionId | POST/PUT 超时不代表未提交；先查结果。专用 submissionId 按该业务契约复用，不生成新 ID 盲目重发 |
| 读取副作用 | 登录更新账号状态；导出写审计；通知测试会真实外发 | 评审与排查不能把这些动作标成“完全只读” |

`version` 位置必须按接口取值。例如管理用户更新/重置密码和大部分删除使用 query；设备、资源等更新通常在 JSON body；`DELETE /api/v1/pdu-connections/{id}` 仍要求 JSON body 中的 version。客户端/网关不能统一删除所有 DELETE 请求体。

本轮 JWT 增加账号版本验证：旧版已签发但没有 userVersion 的 token 需要重新登录。本地密码按 UTF-8 字节限制 8–72，不等同于 8–72 个汉字；登录请求的 JSON 字符串校验与本地 bcrypt 字节边界也不是同一个限制。

普通资源写入、设备上架和库存状态切换不构成通用“请求只执行一次”协议。尤其远端已收到邮件/企业微信而本地尚未落库时，重试可重复发送。当前通知采用至少一次语义和专用去重/锁，不能宣称端到端 exactly once。

## 5. 权限与数据隔离

| 策略 | 实际能力 |
|---|---|
| public | 登录及两个健康检查 |
| system_admin | `/admin`、审批兼容别名、通知配置/测试/投递历史；修改扫码入口配置 |
| asset_role_read_or_manager_write | 资产运营 GET：system_admin / asset_manager / asset_auditor；写入：system_admin / asset_manager；资产审计员可以请求导出，导出会留审计 |
| authenticated_legacy_policy | 核心资源/设备接口保留旧权限：通过登录与当前账号检查；仅“纯 asset_auditor”被禁止写。普通 user 仍可读写核心资源 |

角色检查并未限制到某个站点、数据中心、部门或租户。存在 `permissions` 模型也不等于路由已执行逐 permission 检查。**当前不支持用不同账号实现多客户数据隔离。** 在引入外部系统身份前必须先定义明确的“动作权限 × 资源范围”，并由 service/repository 同时约束列表查询和按 ID 访问，防止仅过滤列表而仍能越权读写单个资源。

新增机器调用身份应具有独立生命周期、窄 scope、可撤销凭证与审计主体。不要把 system_admin 密码写进脚本或让所有集成共用管理员 token。OAuth/OIDC、服务账号、短期客户端凭证或 API key 均未在此版本中实现；选择方案后单独设计并验收。

## 6. 容量与可靠性的实际限制

| 已确认边界 | 依据 / 影响 |
|---|---|
| 设备分页 | `/devices` 支持 page/pageSize，默认 20，pageSize 最大 100；scope 为 PC / ROOM 或空。不要把该筛选当作权限隔离 |
| 固定分页 | 交接历史、资产审计每页 50；通知投递每页 20；不同接口对非法/过大页码处理不统一，应先以各源码和生成契约为准 |
| 许多列表无分页 | 资源树、资产概览、站点/规格/库存/盘点/提醒等；历史增长可导致延迟、内存和 DB 负载持续增加 |
| 同步全量导出 | 多表依次 Find 并在内存组装 JSON；无跨表一致快照保证，不应当作数据库备份或双向同步协议 |
| 固定业务上限 | `MaxDevices=3000`、`MaxDevicesPerRack=20`；属于业务限制，不是经压测得出的系统容量 |
| 导入草稿 | 校验草稿保存在当前进程内存，30 分钟有效、用户/机房绑定、单次使用；重启丢失，多副本不共享 |
| 迁移 | 启动执行 AutoMigrate 与附加约束；已有事务与 advisory lock 串行化，但没有版本化迁移账本、兼容窗口及降级迁移 |
| LDAP 配置 | 本轮加入事务 advisory lock 与 version CAS，防止经本应用并发首存/编辑覆盖；未添加数据库级单例约束，旧重复数据需单独排查，省略 version 的兼容调用也无法识别久远的陈旧编辑。配置审计尚未与写入合成同一事务。BindPassword 在 DB 中是明文，json 隐藏不等于落盘加密 |
| 密钥轮换 | 通知加密密钥由 JWT_SECRET 派生；直接更换该 secret 会影响既有 SMTP/企业微信密文解密。应设计独立密钥、版本与轮换迁移，不得只替换环境变量 |
| 数据约束 | 活跃设备位置唯一与 U 位 GiST 排斥约束防止并发重叠；不能推导所有业务不变量已有 DB 约束 |
| 通知执行 | 仍在 DB 事务中调用外部渠道；网络慢时会拉长事务与连接占用。发送后本地提交失败可重复投递 |
| 故障恢复 | Docker restart 和健康检查不等于高可用；恢复能力需凭恢复演练证明，不能仅凭存在备份文件确认 |

本轮入口加固的目标边界为总请求体 8 MiB、登录 16 KiB、资产运营 1 MiB、最多 128 个活跃 HTTP handler；超大请求/过载需要处理 413 / 503。具体已发布行为以当次源码、发布清单和真实 HTTP 验证为准，OpenAPI 不把反向代理、排队、所有业务查询耗时承诺成 SLA。登录限流是进程内状态；多副本之前需要共享限流或受控网关。

本轮修复和测试不能替代长期安全维护。上线到外部网络前应实际验证 TLS、受控反向代理、网络访问边界、凭证管理、依赖漏洞结果与备份恢复；具体完成状态写进发布证据。Go 构建工具链版本与模块最低版本是两个概念，不应仅因 `go.mod` 兼容旧 Go 就继续使用已停止安全维护的构建器。

## 7. 后续扩展的落地顺序

### P1：下一次接入外部系统前完成

1. **正式输入/输出 DTO。** 把 API 与 GORM 模型拆开；写入仅允许明确白名单字段，禁止关联对象透传。集中限制长度、枚举、分页及 body 大小；明确 PATCH 与 PUT、空值与省略的不同语义。
2. **授权矩阵与资源范围。** 形成逐 API 的读/写/审批/导出权限表，增加仅属于指定数据中心或站点的测试，覆盖 UUID 猜测、批量导出和兼容路由。
3. **版本化数据库迁移。** 显式迁移编号、校验和、迁移锁及前置检查。采用先加字段/双读写/再清理的兼容发布，禁止把旧镜像回滚当成数据库自动回滚。
   同期补齐 LDAP 配置的单例、乐观并发、审计和独立密钥加密；先处理现存多记录与密文/明文迁移，不能只增加一个字段即宣称已有密钥管理。
4. **外部标识与归属。** 设计唯一 `(source_system, entity_type, external_id)` 映射到内部 UUID；定义每个字段谁是主系统、冲突如何合并、删除如何处理。业务显示编号和序列号不保证是永久全局主键。
5. **可恢复写入协议。** 设计持久化幂等表：调用方 + 操作 + 幂等键唯一，保存请求摘要、执行状态、响应结果与有效期。同键不同请求必须冲突；业务写入与幂等结果在同一事务提交。
6. **分页与同步。** 新接口统一 bounded limit 与 cursor、稳定排序（时间 + UUID）；提供变更序号/删除标记及重放规则。避免用当前页码偏移和同步全量导出承担增量同步。

验收要求：完整角色和资源范围矩阵、越权反例、同键并发/超时重试、迁移升级与恢复、分页边界及多客户端契约测试。验收失败前仅允许受控内部联调，不能标记“已具备通用集成能力”。

### P2：第一个集成项目中验证

增加独立集成适配层，HTTP 只负责协议与身份，调用既有 service 执行业务，不直接写业务表。每个适配器明确映射、速率、重试、错误分类和补偿方式。先接一个实际业务系统，用真实字段与失败场景检验设计；不要预先铺开没有消费者的通用框架。

如需要外发事件，在业务事务中同时写 outbox，worker 认领、发送、确认、退避重试，超过阈值进入可观测死信处理。事件至少包含唯一 eventId、schemaVersion、类型、发生时间、资源 ID/版本和关联 ID；敏感数据最小化。接收方必须按 eventId 去重，乱序时按资源版本判断。webhook 需独立验证目标地址、HTTPS、签名、时间窗口、防重放与订阅授权；当前企业微信 webhook 配置不等价于此协议。

### P3：有明确规模需求后完成

将导入草稿和长任务持久化，批量导入/导出改成有进度、结果文件与错误明细的任务。拆出后台 worker，增加认领租约、重启续跑及任务取消。用真实数据压测 DB/连接池/索引/内存，建立 RPO、RTO、延迟与错误率目标，再决定多副本和高可用方案。

## 8. 接力开发的接口变更要求

任何 AI 或开发者更改 API，都必须在 103 工作区的任务交接材料中交付以下证据：

1. 变更前后行为、受影响的消费者，以及属于兼容新增还是破坏性变更。
2. 更新的 OpenAPI、接口清单、错误码清单与生成命令；不得只写“新增接口若干”。
3. 身份、动作权限、资源范围、输入白名单、并发版本和重试语义的明确选择。
4. 路由覆盖检查、相关业务测试、真实 HTTP 验证及未测外部依赖的说明。
5. 对应 commit/tag、迁移编号、镜像摘要、部署结果与可执行回滚/恢复步骤。

破坏性改动必须提供新版本或迁移期；不得在原 `/api/v1` 路径静默改字段类型、删除字段、改变错误码或缩减权限后仅修改网页。兼容别名与正式路径必须使用同一授权策略。所有契约和运行证据保存在 103，交接入口引用服务器路径；AI 的本地工作目录只能作为临时副本。
