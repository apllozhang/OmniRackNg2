## 1. 文档目的与阅读方式

### 1.1 文档目的

本手册用于让新的开发人员、测试人员、部署人员和系统管理员能够在不依赖原始开发者口头记忆的情况下完成以下工作：

- 理解系统解决的问题、功能边界和关键业务决策。
- 在本地启动前端、后端、PostgreSQL 以及可选 LDAP 联调服务。
- 修改数据中心、机房、机柜、设备、模板、PDU、用户和审批相关代码。
- 分析 U 位重叠、编码回退、导入重复、权限越权、布局错位、登录失败等问题。
- 执行单元测试、组件测试、端到端测试、类型检查、静态检查和生产构建。
- 将经过验证的代码打包部署到服务器，并进行健康检查和回滚。
- 在后续需求中保持前后端字段、导入导出格式、权限模型和数据库约束一致。

### 1.2 使用原则

1. **以后端契约为主**：设备字段、状态、枚举、校验和错误语义首先以 Go model/service/handler 与 OpenAPI 为准，前端类型和表单只能适配后端，不能私自创造同义字段。
2. **先读规则再改代码**：涉及资源层级、位置、批量导入、复制、移动、权限和删除的改动，先阅读本文件对应章节和 `backend/api/openapi.yaml`。
3. **每次改动必须验证**：至少执行受影响模块测试；涉及接口必须执行后端测试和前端构建；涉及页面交互必须执行组件测试或已登录 Playwright 流程。
4. **生产数据优先保护**：不直接在生产库手工改业务表；必须经过服务层或经过审批的迁移脚本，并提前备份。
5. **不记录敏感值**：日志、截图、测试报告和文档不得包含密码、Token、Bind 密码、完整 Cookie 或生产数据库连接串。

### 1.3 文档与代码的关系

本文是维护说明，不替代代码注释、OpenAPI 契约和数据库实际结构。出现差异时按以下优先级处理：

1. 运行中的后端接口行为和数据库实际结构；
2. `backend/api/openapi.yaml`；
3. 后端 model/service/repository 测试；
4. 前端 API 类型和组件测试；
5. 本文档和其他说明文档。

发现差异后应修正代码或文档，并在提交说明中写明原因。

## 2. 项目定位与当前能力

### 2.1 项目定位

机柜管理工具是一个面向数据中心基础设施的资源管理平台，核心对象为：

```text
数据中心 → 机房 → 机柜 → 统一 U 位 → 设备
                                      └→ PDU 供电连接（可选）
```

系统将后台资源台账和机房大屏结合：后台负责数据的增删改查、生命周期、权限、导入和审计；大屏负责机柜布局、U 位状态可视化、快捷操作、设备定位、容量分析和机柜图导入导出。

### 2.2 当前功能清单

#### 资源层级

- 数据中心、机房、机柜的增删改查。
- 资源编码自动生成或手工填写。
- 资源状态管理、软删除和乐观锁。
- 数据中心复制、机房复制、机柜复制。
- 机房之间、数据中心之间移动机房或机柜。
- 父资源存在子资源时禁止直接删除，避免孤儿数据。
- 大屏直接新增、编辑、查看和删除机柜。

#### 机房大屏

- 按机房配置的 `racksPerRow` 自动换行。
- 每个机柜使用固定格位，不允许视觉上互相重叠。
- 支持拖动机柜调整位置，并可实现两个机柜交换格位。
- 机柜和 U 位使用统一模型，不区分正面和背面。
- 左键点击 U 位打开统一操作菜单；有设备时可查看详情、编辑、迁移、下架等，空 U 位可上架设备。
- 按设备名搜索并定位到目标机柜和 U 位，搜索框后提供明确的查询按钮。
- 机柜详情采用左侧机柜图、右侧参数和容量利用率的双栏布局。
- 机柜图可导出 Excel，并可将同一格式文件回导。

#### 设备与机柜

- 设备类型、设备台账、分页和筛选。
- 统一设备编辑表单同时服务设备台账和大屏。
- 统一设备详情字段和显示语义。
- 设备上架、迁移、下架、位置履历。
- 管理 IP、业务 IP、SN、功耗、尺寸、责任信息等字段统一由后端定义。
- 设备编号支持自动生成；已有设备编辑时不自动换号。
- 设备批量导入；设备信息导出后修改再导入更新。

#### 模板与批量处理

- 标准 42U 机柜模板。
- 自定义机柜模板及不可变模板版本。
- 机柜和设备 Excel 模板下载、字段说明、统一映射和校验。
- 普通机柜/设备批量导入不强制提供编码，缺失时由后端生成。
- 导出的机柜图可作为同格式导入源；回导前执行身份冲突、重名、换位、删除和替换验证。

#### PDU 与容量分析

- PDU 实例、插座和设备供电连接关系。
- 插座类型区分国标、欧标、10A、16A 等类型；不是强制参数。
- 可计算 U 位、额定功耗、峰值功耗、承重、PDU/插座相关利用率。
- 缺少计算所需数据时显示“无法计算”，并说明缺失原因；禁止将未知值静默当作 0。

#### 管理、安全和集成

- 本地账号密码登录、JWT、bcrypt。
- RBAC、管理员专属用户管理和审批设置。
- LDAP 真实服务联调、服务账号绑定、用户搜索、密码校验、组查询和组到角色映射。
- 关键变更写入审计日志。
- 软删除、版本号、位置唯一性和 U 位范围排除约束。

## 3. 业务边界与已确认决策

### 3.1 资源数量上限已经取消

已取消以下固定业务上限：

- 数据中心数量上限 15。
- 每个数据中心的机房数量上限 5。
- 系统机柜总数上限 200。

当前代码和后端接口不得重新加入上述限制，也不得通过前端计数偷偷阻止创建。数据库中也不应保留用于执行这些固定上限的约束、计数器或配置项。

但“取消固定资源上限”不等于系统无限承载。实际仍受到：

- PostgreSQL 存储空间、连接数、索引体积和事务吞吐。
- 后端内存、CPU、并发请求和 JSON 响应大小。
- 浏览器一次性渲染的机柜数量、DOM 数量和大屏布局计算量。
- Excel 文件大小、行数和解析内存。
- 网络带宽、反向代理超时和容器资源配额。

这些是容量规划和运行资源问题，不应伪装成固定业务上限。

### 3.2 仍保留的内部业务校验

以下校验与资源总量上限不同，应继续保留：

- `racks_per_row` 的布局合法范围为 `1..20`，用于控制大屏每排机柜数量。
- 机柜 U 位必须为正整数，设备占用区间不能超出机柜容量。
- 同一设备不能同时拥有多个活动位置。
- 同一机柜的活动设备位置不能发生 U 位区间重叠。
- 受当前模型约束的单柜设备数量、设备占用 U 数、功耗或承重字段校验不能因取消资源数量上限而一并删除；如业务确实要放宽，必须单独提出需求并评估数据库和 UI 性能。
- 父资源有子资源时，删除操作必须阻止或提供明确的级联策略，不能留下孤儿记录。

### 3.3 全系统取消正面/背面维度

用户已确认“正背面逻辑全系统彻底取消”。维护时遵循：

- 新接口、前端路由、表单、导入模板和导出模板不得把正面/背面作为必填业务维度。
- U 位只表达一个连续的机柜空间区间。
- 历史数据库中的 `face` 字段可以暂时作为兼容字段存在，但不得用于新的业务分支或唯一性判断。
- `orientation` 如果出现在设备字段中，`NORMAL/REVERSE` 表示设备安装方向，而不是正面/背面。
- 清理历史字段必须使用可审计迁移，先确认线上历史数据，再决定保留兼容列、迁移值或最终删除；不能仅删除前端字段。

### 3.4 编码自动生成策略

新增数据中心、机房、机柜、设备和模板时，默认可以自动生成编码。建议格式如下：

| 对象 | 默认前缀 | 示例 |
|---|---|---|
| 数据中心 | `DC-` | `DC-XXXXXXXXXXXX` |
| 机房 | `ROOM-` | `ROOM-XXXXXXXXXXXX` |
| 机柜 | `RACK-` | `RACK-XXXXXXXXXXXX` |
| 设备 | `DEV-` | `DEV-XXXXXXXXXXXX` |
| 机柜模板 | `TPL-` | `TPL-XXXXXXXXXXXX` |

自动生成由后端执行，前端只能显示预览或允许关闭后手工输入。编辑已有记录不得因为重新打开表单或保存其他字段而自动更换已有编码。批量导入中编码可以为空；后端在创建路径生成，更新路径必须先根据稳定身份匹配记录。

## 4. 系统架构总览

### 4.1 逻辑架构

```text
浏览器
  │ HTTPS/HTTP
  ▼
Nginx（frontend 容器）
  │ /api 反向代理
  ▼
Gin REST API（backend 容器）
  ├─ middleware：JWT、角色、审计上下文、错误处理
  ├─ handler：参数解析、响应封装
  ├─ service：业务规则、事务编排、导入导出、认证
  ├─ repository：GORM 查询和持久化
  └─ model：数据库实体与请求/响应结构
       │
       ├─ PostgreSQL：业务数据、审计和位置约束
       └─ PostgreSQL：业务数据持久化（当前唯一业务数据库）

可选联调：
  backend ── LDAP 协议 ── OpenLDAP 容器
```

### 4.2 前后端通信

- 前端使用 Axios 封装 REST 请求。
- Token 存放在浏览器 `localStorage.cabinet_access_token`。
- 请求拦截器附加 Bearer Token；响应拦截器统一处理未登录和错误消息。
- 后端返回统一响应结构，成功和失败均应通过 `response` 包装，避免页面各自猜测字段。
- 文件下载使用 Blob；导入使用 multipart/form-data 上传 Excel。
- 页面数据应在请求成功后以服务端响应为准刷新，不以本地乐观修改替代最终结果。

### 4.3 事务原则

涉及以下操作时必须使用后端事务：

- 创建/更新资源及审计日志。
- 上架、迁移、下架及位置履历。
- 机房或机柜移动及关联设备位置更新。
- 复制资源树及其子级。
- 机柜图导入正式提交。
- PDU 连接创建、替换或删除。
- 用户角色修改、管理员保护逻辑和审批处理。

校验阶段可以不写库，但正式提交必须使用单次草稿、版本快照和数据库事务，避免重复提交和半成功状态。

## 5. 代码目录与文件职责

### 5.1 根目录

| 路径 | 职责 |
|---|---|
| `README.md` | 项目入口、功能基线、文档索引、常用命令 |
| `docker-compose.yml` | PostgreSQL、backend、frontend、可选 LDAP/dev 服务编排 |
| `.env` | 本地或服务器环境变量，不应提交真实密钥 |
| `.gitignore` | 构建产物、环境文件、依赖目录和测试输出忽略规则 |
| `backend/` | Go 后端服务 |
| `frontend/` | Vue 3 前端应用 |
| `deploy/` | Docker/LDAP 部署说明和联调资源 |
| `scripts/` | 启停和阶段性运维脚本 |
| `docs/` | 需求、开发、维护文档 |
| `assets/` | 设计或导入导出相关静态资源 |

### 5.2 后端目录

典型职责分层如下：

```text
backend/
├─ cmd/server/main.go              # 进程入口、配置、数据库、迁移、路由启动
├─ internal/config/                # 环境变量解析和默认配置
├─ internal/router/                # Gin 路由注册和中间件装配
├─ internal/handler/               # HTTP 入参、调用 service、响应输出
├─ internal/service/                # 业务用例、事务、规则、导入导出
├─ internal/repository/             # GORM 查询、保存、事务辅助
├─ internal/model/                  # GORM 实体、枚举、请求响应结构
└─ internal/response/               # 统一成功/错误响应
```

维护要求：

- handler 不直接拼复杂业务 SQL，不绕过 service 写位置表。
- service 不依赖 HTTP 类型；需要的输入使用 service command/DTO。
- repository 不实现权限判断和业务审批；只负责可靠持久化和查询。
- model 中字段改动必须同步 OpenAPI、前端 types、表单、导入映射和测试。
- 大型 service 拆分后保持事务入口清晰，避免把一个业务用例拆成多个无法原子回滚的请求。

### 5.3 前端目录

```text
frontend/src/
├─ api/                            # Axios API 模块和接口调用
├─ components/                     # 可复用对话框、表单、表格、布局组件
├─ features/                       # 按领域组织的导入、布局、容量分析等逻辑
├─ layouts/                        # 登录后和公开页面布局
├─ router/                         # 路由、懒加载和权限入口
├─ stores/                         # Pinia 状态，如 auth
├─ types/                          # 后端契约对应的 TypeScript 类型
├─ utils/                          # Excel、字段映射、格式化、校验和通用函数
├─ views/                          # 页面级组件
├─ App.vue                         # 应用壳
└─ main.ts                         # Vue、Element Plus、路由和 store 初始化
```

前端维护时优先复用统一组件和 feature 工具，避免在 `RoomScreenView.vue`、设备台账页和模板页中复制一套相似表单或 Excel 解析逻辑。

### 5.4 重要维护入口

- 启动和迁移：`backend/cmd/server/main.go`。
- 配置默认值：`backend/internal/config/config.go`。
- 路由和鉴权链：`backend/internal/router/router.go`。
- 资源及设备接口：`backend/internal/handler/`、`service/`、`repository/`。
- REST 契约：`backend/api/openapi.yaml`。
- 大屏入口：`frontend/src/views/` 中的机房屏幕视图及拆分后的子组件/features。
- 统一设备表单：`frontend/src/components/` 中的设备编辑组件，台账和大屏共同使用。
- Excel 逻辑：`frontend/src/utils/`、`frontend/src/features/` 中的模板、映射、校验和导入预览代码。

## 6. 运行环境与 Docker 服务

### 6.1 Compose 服务

| 服务 | 容器名 | 默认端口 | 作用 | 是否默认启动 |
|---|---|---:|---|---|
| postgres | `cabinet-postgres` | 5432 | 主业务数据库 | 是 |
| （已移除） | — | — | 后端当前无 Redis 业务依赖 | 否 |
| backend | `cabinet-backend` | 8080 | Go REST API | 是 |
| frontend | `cabinet-frontend` | 5173→80 | Nginx 静态前端和 API 代理 | 是 |
| ldap | `cabinet-ldap` | 1389→389 | OpenLDAP 真实联调 | 否，`ldap` profile |
| go-dev | `cabinet-go-dev` | 2222、8081 | 本地 Go 开发容器 | 否，`dev` profile |

### 6.2 启动命令

在项目根目录执行：

```bash
docker compose up -d postgres backend frontend
docker compose ps
docker compose logs --tail=200 backend
docker compose logs --tail=200 frontend
```

启动 LDAP 联调：

```bash
docker compose --profile ldap up -d ldap
```

启动开发容器：

```bash
docker compose --profile dev up -d go-dev
```

停止默认服务：

```bash
docker compose stop
```

停止并删除容器但保留命名卷：

```bash
docker compose down
```

**注意**：不要在未确认备份和卷用途的情况下执行 `docker compose down -v`；该命令会删除 PostgreSQL 或 LDAP 数据卷，属于破坏性操作。

### 6.3 健康检查

后端健康接口通常分为：

- `/health/live`：进程存活，不代表数据库可用。
- `/health/ready`：依赖可用性检查，至少应验证数据库连接。

前端检查首页或 Nginx：

```bash
curl -I http://127.0.0.1:5173/
curl -i http://127.0.0.1:8080/health/live
curl -i http://127.0.0.1:8080/health/ready
```

生产环境还应从用户实际访问地址验证：登录、资源列表、机房大屏、导入预览和文件下载，而不只看容器为 `Up`。

## 7. 环境变量、密钥与配置管理

### 7.1 常用配置

| 变量 | 用途 | 维护建议 |
|---|---|---|
| `DATABASE_URL` | 后端连接 PostgreSQL | 仅注入运行环境，不提交真实值 |
| `HTTP_ADDR` | API 监听地址 | 容器内通常为 `:8080` |
| `POSTGRES_USER` | 数据库用户 | 生产使用专用最小权限账号 |
| `POSTGRES_PASSWORD` | 数据库密码 | 使用密钥管理，不写文档 |
| `POSTGRES_DB` | 数据库名 | 与备份脚本保持一致 |
| `JWT_SECRET` | JWT 签名密钥 | 首次部署缺失时由部署脚本自动生成并持久化；生产环境可显式覆盖，轮换要有计划 |
| `JWT_EXPIRE` | Token 有效期 | 按安全策略设置 |
| `GOPROXY` | Go 依赖下载代理 | 网络受限环境配置镜像或内部代理 |
| `NPM_REGISTRY` | 前端依赖下载源 | 网络受限环境配置内部镜像 |
| `LDAP_*` | LDAP 地址、Base DN、Bind 账号和映射 | 密码不回显，改动后重新连接测试 |
| `LDAP_HOST_PORT` | LDAP 宿主映射端口 | 避免与已有目录服务冲突 |
| `RACKS_PER_ROW` 或房间字段 | 大屏默认布局 | 房间显式值优先；`0` 的语义必须保持，不得被无条件替换为 8 |

### 7.2 配置优先级

建议遵循：

1. 业务实体上已经保存的显式值；
2. 请求中明确提供的值；
3. 系统配置文件或环境变量；
4. 仅在“字段未提供”时使用默认值。

特别注意 `racksPerRow=0`：必须区分“未提供”和“显式提供 0”。不能使用简单的 `value || 8`、Go 中无条件 `if value == 0 { value = 8 }` 或数据库读出后统一替换。当前业务布局参数仍需要通过合法性校验；若产品允许 0 表示自动布局，应在契约中明确“0=自动”并单独实现，而不是把它静默变成 8。

### 7.3 密钥安全

- `.env`、生产 compose 覆盖文件、LDAP bind 密码、管理员初始密码不得提交 Git。
- 日志只能记录配置是否存在，如 `hasBindPassword`，不能打印密码。
- 前端不保存 LDAP Bind 密码。
- JWT 过期、密钥轮换和管理员密码重置必须有运维记录。
- 测试用密码和服务器密码必须完全分离。

## 8. 后端分层与请求处理链路

### 8.1 标准链路

```text
HTTP 请求
  → Gin 路由
  → CORS/日志/恢复中间件
  → JWT 解析
  → 角色/管理员权限检查
  → Handler 参数解析和基础校验
  → Service 用例与事务
  → Repository 查询/写入
  → PostgreSQL 约束
  → 统一响应
```

### 8.2 Handler 维护要点

Handler 应负责：

- 读取 path/query/body/multipart 参数。
- 调用统一绑定和基础格式校验。
- 从上下文获取当前用户和角色。
- 调用 service，并把领域错误映射成 HTTP 状态码。
- 对文件下载设置正确的 Content-Type、Content-Disposition。

Handler 不应负责：

- 根据前端显示字段拼接多个表的复杂更新。
- 自己判断 U 位是否重叠后直接插入位置表。
- 直接修改数据库跳过审计、审批和版本号。
- 仅用前端传来的角色字段决定管理员权限。

### 8.3 Service 维护要点

Service 是规则的唯一落点：

- 资源 CRUD：检查编码、父级归属、状态、删除条件和版本号。
- 位置服务：锁定机柜/设备活动位置，校验区间，写位置履历。
- 复制服务：新 ID、新编码、规划状态、明确不复制唯一资产信息。
- 移动服务：变更父级及其关联位置归属，清理目标大屏坐标，保证原子性。
- 导入服务：解析、规范化、身份匹配、冲突分类、草稿确认、事务提交。
- 认证服务：密码校验、LDAP 回退/映射、JWT 签发。
- 管理服务：用户、角色、审批配置和最后管理员保护。

大型 service 拆分后，建议保持“一个 HTTP 用例一个事务入口”，内部再调用细分的领域服务；不要把一个复制操作拆成前端连续调用多个公开接口。

### 8.4 Repository 维护要点

- 默认查询过滤 `deleted_at IS NULL`。
- 更新带 `version` 条件，影响行数为 0 时返回乐观锁冲突。
- 活动位置查询必须明确状态，不把历史履历当当前占用。
- 复杂列表要预加载必要关联，避免 N+1。
- 统一分页参数和排序白名单，禁止将用户输入直接拼 SQL。
- 数据库约束错误需转换为稳定领域错误，前端不应依赖 PostgreSQL 原始错误文本。

### 8.5 AutoMigrate 现状

`backend/cmd/server/main.go` 启动时调用 `repository.Migrate(db)`。当前迁移过程包括：

- 创建 `btree_gist` 扩展。
- GORM `AutoMigrate` 核心模型。
- 活动设备资产编号唯一索引。
- 活动设备位置唯一索引。
- 活动 U 位范围排除约束。
- 历史 `face` 字段的兼容处理。

`backend/migrations/` 中的 SQL 是参考和演进记录，尚未完全替代启动时 AutoMigrate。生产长期维护建议改成显式、版本化、可审计、可回滚策略：启动只检查版本，不在每次启动隐式改表；迁移失败时阻止应用接收流量。

## 9. 前端页面、路由与组件

### 9.1 页面职责

前端页面按业务领域组织，主要包含：

- 登录页：本地/LDAP 登录，错误提示和 Token 建立。
- 工作台/资源树：数据中心、机房、机柜层级浏览。
- 数据中心管理：新增、编辑、删除、复制、跨层级移动入口。
- 机房管理：机房参数、状态、`racksPerRow` 配置和大屏入口。
- 机柜模板：模板 CRUD、版本、规格参数、默认值和模板下载。
- 机柜/设备台账：列表、筛选、批量导入、导出设备信息、编辑统一表单。
- 机房大屏：布局、搜索定位、U 位操作、详情、机柜图导入导出。
- 管理员：用户、角色、审批策略、LDAP 配置和连接测试。

### 9.2 路由和懒加载

路由使用动态 import 进行页面级懒加载，避免首屏一次性加载全部管理页面。维护新页面时：

- 使用路由级 `() => import(...)`。
- 不把大型 Excel 库或管理员页面静态打入首屏 chunk。
- 对大屏和导入页面检查 chunk 是否合理、网络慢时是否仍可显示加载状态。
- 权限检查必须在路由和后端同时存在；懒加载不是权限控制。

### 9.3 大屏交互统一原则

- 左键点击统一打开菜单，避免有设备 U 位点击无反应。
- 空 U 位菜单显示“上架设备”等适合空位的操作。
- 有设备 U 位菜单显示查看详情、编辑设备、迁移、下架等操作。
- 点击机柜状态信息可以修改状态，但最终由后端权限和版本校验决定。
- 菜单定位不能超出可视区域；点击外部关闭；键盘操作和 Esc 关闭需保持可用。
- 不再为正面/背面维护两套视图或点击坐标。

### 9.4 统一设备编辑表单

设备台账和大屏必须调用同一个设备编辑表单组件及同一个字段 schema：

- 新增、编辑、详情字段名称一致。
- 字段格式化、必填规则、枚举、单位和错误提示一致。
- 表单提交使用后端字段名，不在页面中做隐式别名转换。
- 详情页只读渲染应复用相同字段元数据，避免“编辑能看到、详情看不到”或相反。
- 任何字段新增要同时更新 API 类型、schema、表单、详情、导入映射、导出列和测试。

## 10. 数据模型与关系约束

### 10.1 核心表

| 表 | 说明 | 关键维护点 |
|---|---|---|
| `users` | 本地用户、LDAP 映射、启停状态 | 密码 bcrypt；软删除；保护最后启用管理员 |
| `roles` | 角色定义 | 管理员角色为 `system_admin` |
| `permissions` | 权限定义 | 新权限要同步前后端和初始化数据 |
| `user_roles` | 用户角色关联 | 更新需审计，接口需权限保护 |
| `role_permissions` | 角色权限关联 | 禁止普通用户自行修改 |
| `audit_logs` | 操作审计 | 记录操作者、动作、对象、结果和时间 |
| `ldap_configs` | LDAP 连接和映射配置 | Bind 密码只写不读；接口只返回 `hasBindPassword` |
| `data_centers` | 数据中心 | 编码唯一、软删除、状态、版本 |
| `rooms` | 机房 | 归属数据中心、`racks_per_row`、状态、版本 |
| `racks` | 机柜 | 归属机房、规格、屏幕坐标、排序、模板快照 |
| `rack_templates` | 机柜模板 | 模板编码和当前版本信息 |
| `rack_template_versions` | 不可变模板版本 | 发布后不能静默改变已有机柜 |
| `device_types` | 设备类型 | 型号和规格默认值来源 |
| `devices` | 设备台账 | 资产/设备编号、名称、SN、状态、规格和网络信息 |
| `rack_device_positions` | 当前活动设备位置 | 一个设备一个活动位置；U 区间不能重叠 |
| `rack_u_occupancies` | 统一 U 位占用视图/实体 | 不区分正面和背面 |
| `device_position_histories` | 设备位置履历 | 上架、迁移、下架均形成可追溯记录 |
| `operation_policies` | 操作审批配置 | 管理员维护；默认审批关闭 |
| `approval_records` | 审批记录 | 状态、申请人、审批人和对象快照 |
| `pdus` | PDU 实例 | 机柜归属、容量/规格信息 |
| `pdu_sockets` | PDU 插座 | 国标/欧标、10A/16A 等类型 |
| `pdu_connections` | 设备供电关系 | 可选；用于容量和供电分析 |

### 10.2 公共字段

多数业务表具有以下维护语义：

- UUID 主键：对外不要使用自增 ID 作为资源身份。
- `created_at`、`updated_at`：由后端统一写入。
- `deleted_at`：软删除时间；列表默认排除，恢复能力需单独设计。
- `version`：乐观锁版本，更新请求带上读取时版本。
- 创建人/更新人或审计上下文：用于责任追踪。

前端不要把 `null`、空字符串、0 和字段缺失混成一个状态。特别是数值 0 可能是合法业务值，缺失应使用 `null` 或明确的未提供语义。

### 10.3 层级关系

```text
data_centers (1) ──< rooms (N)
rooms (1)        ──< racks (N)
racks (1)        ──< rack_device_positions (N)
devices (1)      ──< rack_device_positions (0..1 active)
racks (1)        ──< pdus (N)
pdus (1)         ──< pdu_sockets (N)
devices (1)      ──< pdu_connections (N)
```

删除父级前必须查询活动子级：

- 有机房的数据中心不可直接删除。
- 有机柜的机房不可直接删除。
- 有活动设备或 PDU 的机柜不可直接删除。
- 删除设备前需处理活动位置、供电连接和履历策略。

### 10.4 唯一性

活动数据范围内通常要求：

- 数据中心编码唯一。
- 同层级资源编码唯一或按后端明确作用域唯一。
- 活动设备资产编号/设备编号唯一。
- 活动设备位置唯一：一个设备最多一个活动位置。
- 同一机柜活动 U 区间不可重叠。
- PDU 插座编号在同一 PDU 内唯一。
- 导入中的稳定身份、编码、SN 等冲突必须在预览阶段报告，不能靠数据库报错后猜测。

### 10.5 软删除与查询

软删除对象不应出现在默认下拉、资源树、机柜图和活动位置中。维护查询时应明确：

- 是否只读活动数据。
- 是否需要包含已归档数据。
- 是否需要包含历史位置。
- 是否允许管理员查看已删除对象。

不要为了“方便”移除 `deleted_at` 条件，因为这会造成已删除设备重新出现在大屏或导入匹配列表中。

## 11. 核心业务规则

### 11.1 资源 CRUD

创建：

1. 校验父资源存在且未删除。
2. 处理自动编码或校验手工编码。
3. 规范化名称、状态、数值和可选字段。
4. 写入资源和审计日志。
5. 返回服务端完整对象。

更新：

1. 读取目标对象和当前 `version`。
2. 校验操作者权限、状态转移和父级关系。
3. 只更新请求中明确提供的字段。
4. `WHERE id = ? AND version = ?`，成功后版本递增。
5. 记录变更前后摘要。

删除：

1. 校验资源版本。
2. 检查子资源、活动设备、PDU 和审批记录。
3. 默认软删除。
4. 保留审计和位置历史。
5. 删除失败必须给出可读原因。

### 11.2 状态转移

状态不是任意字符串。新增状态或改变状态流转时，必须同时修改：

- 后端枚举和 service 校验。
- OpenAPI schema。
- 前端类型、下拉选项和颜色映射。
- Excel 解析和错误提示。
- 状态转移测试。
- 维护文档的枚举速查表。

`ARCHIVED` 已确认代表完整归档流程，而不是普通“隐藏”。进入归档前要明确设备位置、关联关系、可否再次激活和审计要求；不能把归档当成简单的前端筛选状态。

### 11.3 设备位置模型

设备位置由机柜和连续 U 区间表达：

- `start_u`：起始 U 位。
- `u_height`：占用高度。
- 结束 U 位可计算为 `start_u + u_height - 1`。
- 设备只能处于一个活动位置或不在架状态。
- 上架/迁移要检查目标机柜容量、目标区间和设备状态。
- 下架应关闭活动位置，新增位置履历，不能物理删除历史。

所有位置变化必须进入位置 service；禁止在页面直接调用 repository 或直接更新位置表。

### 11.4 并发一致性

数据库使用 `btree_gist`、`int8range` 和 EXCLUDE 约束防止并发区间重叠；应用层还应：

- 在位置操作事务内锁定目标机柜和设备当前位置。
- 捕获约束冲突并返回“目标 U 位已被占用”，而不是 500。
- 使用版本号防止两个页面互相覆盖机柜参数或坐标。
- 导入提交前重新读取版本快照，预览通过后若数据已变更则要求重新验证。

### 11.5 复制规则

复制是新资源，不是数据库盲目深拷贝：

- 生成新的资源 ID。
- 新编码自动生成，或根据明确规则产生不冲突编码。
- 副本默认处于规划中/待配置状态。
- 不复制设备、序列号、资产编号和其他唯一资产信息。
- 机柜模板来源可复制，但模板版本保持不可变。
- PDU 实例和设备供电关系默认不复制，避免形成重复资产；若未来需要复制“结构”，也要明确是否只复制插座结构而非实例。
- 整个复制树应在一个事务中完成，失败则全部回滚。

## 12. 大屏、机柜拖动与布局

### 12.1 布局目标

机房大屏需要同时满足：

- 每个机柜都有固定显示框。
- 机柜之间不得重叠。
- 机柜可拖动调整位置。
- 可以通过拖动交换 02 和 03 等机柜的格位。
- 机柜数量增长时自动扩容和换行。
- 第 9、第 10 个机柜等跨行场景背景连续、尺寸一致、对齐正常。
- 第一个机柜不能因特殊 CSS 或首项样式变大。

### 12.2 `racksPerRow`

`racksPerRow` 是房间级布局参数，含义是每排最多展示多少个机柜。它属于布局，不是资源总数上限。

维护要点：

- 读取房间显式值，不能无条件回退为 8。
- 合法范围按当前契约校验为 `1..20`；如果未来要支持 0=自动，必须修改 API、后端、前端和测试的完整语义。
- 保存后再次打开必须从后端读取持久化值。
- 修改 12、16 等值后，页面刷新和重新进入都要保持。
- 布局网格应按实际机柜数量计算行列，不能写死前 8 个或前 9 个。

### 12.3 拖动与交换

推荐流程：

1. 页面根据 `position/order` 把机柜映射到固定格位。
2. 拖动开始时保存源机柜 ID、源格位和屏幕坐标。
3. 拖动经过目标格位时显示插入/交换提示，不允许覆盖已有机柜。
4. 放下后前端生成“位置交换/排序更新”请求。
5. 后端校验房间版本、目标格位唯一性和坐标边界。
6. 成功后以服务端顺序刷新；失败时恢复拖动前快照并提示原因。
7. 机柜移动到其他房间时清空原房间坐标，避免目标房间复用旧坐标造成重叠。

不要只保存 CSS `transform` 而不保存业务位置；不要把 DOM 索引当作长期身份。机柜 ID 才是稳定身份，格位是可变属性。

### 12.4 U 位交互

统一左键交互：

- 空 U 位：上架设备、查看机柜信息、查看可用区间。
- 有设备 U 位：设备详情、编辑设备、迁移设备、下架设备。
- 点击机柜状态标签：在有权限时打开状态编辑；无权限时只读并提示。
- 右键不再承担核心功能，以避免浏览器上下文菜单、触摸设备和无障碍交互不一致。

菜单动作必须带目标对象 ID 和当前版本，不使用当前鼠标位置反查对象。

### 12.5 搜索定位

设备名搜索流程：

1. 用户输入设备名称。
2. 点击查询按钮或按 Enter。
3. 请求后端设备搜索/位置查询接口。
4. 返回设备、数据中心、机房、机柜、起始 U 和占用高度。
5. 页面切换到对应机房（如需要），高亮机柜和 U 区间。
6. 设备不存在、未上架或名称重复时分别提示。

搜索结果不要只在前端当前列表过滤，否则分页、未加载机房和大屏换房时会出现“查不到”。

## 13. 机柜模板与规格快照

### 13.1 模板职责

机柜模板用于提供创建机柜时的默认结构和规格，不是实时引用。常见字段包括：

- 模板编码、名称、版本和状态。
- U 位总数。
- 宽度、深度、高度和单位。
- 承重、额定功耗或其他容量参数。
- PDU 默认信息。
- 可选描述和厂商信息。

### 13.2 模板版本不可变

发布后的模板版本不可直接修改。修改流程：

1. 复制当前版本或创建新草稿版本。
2. 调整 U 位、宽度、深度、高度、承重、电源等参数。
3. 校验版本完整性。
4. 发布新版本。
5. 新建机柜可选择新版本。
6. 既有机柜保留创建时的 `templateSnapshot`，不被静默修改。

### 13.3 机柜实例覆盖

创建机柜时：

- 模板字段只作为默认值。
- 用户在新增表单中调整的宽度、深度、高度、U 位、承重、PDU 等实例参数优先保存。
- 后端再次校验最终实例规格，不能只校验模板。
- 编码为空且开启自动生成时，由后端生成 `RACK-...`。

常见 bug 来源是前端表单只显示模板值、提交时丢掉用户覆盖值，或后端 update DTO 没有接收新字段。处理此类问题时要同时检查：表单初始值、`v-model` 类型、请求 payload、handler 绑定、service 更新白名单、repository 更新字段和数据库列。

## 14. 设备台账与统一编辑模型

### 14.1 后端字段优先

设备字段以后端 model 和 API 为准。前端不得同时维护 `deviceName/name`、`managementIp/mgmtIp` 等多个含义不清的别名。若历史数据存在旧字段，统一在后端 DTO 或迁移层进行兼容映射，前端只消费一个规范字段。

### 14.2 统一字段类别

实际字段以 OpenAPI 为最终依据，维护时至少按以下类别检查：

- 身份：设备 ID、设备编号/资产编号、设备名称、设备类型、厂商、型号。
- 识别：SN、标签、业务系统标识。
- 位置：机柜 ID、机柜编码、起始 U、U 高度、安装方向（若仅代表设备方向）。
- 网络：管理 IP、业务 IP，可按后端定义为字符串、列表或结构化值。
- 能耗：额定功耗、峰值功耗、功耗单位。
- 规格：宽度、深度、高度、重量、承重相关信息。
- 供电：PDU、插座连接，插座类型为可选。
- 生命周期：状态、上线/下线时间、责任人、备注。
- 审计：创建/更新时间、创建人、更新人、版本。

### 14.3 编辑和详情一致性

设备台账、大屏设备菜单、设备详情必须共享：

- 同一 TypeScript 类型。
- 同一字段 schema/元数据。
- 同一格式化函数和单位显示。
- 同一错误和必填规则。
- 同一保存 API。

详情页缺失字段时，不要另写一组硬编码标签；从 schema 渲染只读字段。新增字段验收应包括：台账可见、大屏编辑可见、详情可见、Excel 导出可见、导入可更新、后端返回和测试覆盖。

### 14.4 设备编号规则

- 新增设备且编码为空：后端自动生成。
- 设备编辑：不因修改名称、IP、SN 或位置自动换编码。
- 设备信息导出后再导入：以稳定身份优先匹配原设备，允许更新管理 IP、业务 IP 和其他可编辑字段。
- 编号变更时：导入验证必须询问是新设备还是原设备改名/改编号，不能直接覆盖或重复创建。
- SN、资产编号等唯一信息冲突必须阻止提交或要求明确处理。

## 15. PDU、插座与供电关系

### 15.1 数据模型

```text
rack → pdus → pdu_sockets
device ──< pdu_connections >── pdu_socket
```

PDU 和插座信息是增强能力，不是机柜或设备的强制创建参数。允许先维护设备和机柜，再补充供电信息。

### 15.2 插座类型

当前需求要求可区分：

- 国标。
- 欧标。
- 10A。
- 16A。

实际实现可用组合枚举或独立字段表达，但必须在后端明确规范化方式。不要让前端随意发送多个同义中文字符串。未知或未配置时使用“未设置”，不能当成某种插座类型。

### 15.3 容量计算

详情页可展示：

- U 位利用率：已占用 U / 机柜总 U。
- 设备额定功耗利用率：设备额定功耗合计 / 机柜可用额定功耗。
- 峰值功耗利用率：设备峰值功耗合计 / 机柜可用峰值或额定容量。
- 承重利用率：设备重量合计 / 机柜承重。
- PDU 利用率：已连接功耗 / PDU 容量，或按插座使用情况统计。
- 插座利用率：已占用插座数 / 插座总数。

每项计算需有完整分子和分母。缺失原因示例：

- 机柜未填写总 U。
- 设备未填写 U 高度或位置。
- 机柜未填写额定功耗容量。
- 设备未填写额定功耗。
- 机柜未填写承重。
- 设备未填写重量。
- PDU 未配置容量。
- 设备没有供电连接。

展示格式应区分“0%”与“无法计算”。

## 16. Excel 导入导出维护规范

### 16.1 总体原则

Excel 是面向用户的交换格式，不是数据库备份格式。所有导入都必须经过：

```text
上传文件 → 文件类型/大小校验 → 表头识别 → 字段映射 → 行级规范化
→ 必填/枚举/格式校验 → 身份匹配 → 冲突分类 → 用户确认
→ 版本复核 → 单事务提交 → 结果报告
```

校验阶段不能写入业务数据；预览结果应可重复、可下载错误报告，并显示每一行的处理建议。

### 16.2 模板设计

模板必须清楚标识：

- 字段中文名。
- 后端字段名或稳定映射名。
- 是否必填：创建、更新分别说明。
- 数据类型和单位。
- 枚举允许值。
- 示例值。
- 业务说明。
- 自动生成规则。
- 是否允许为空清空原值。

建议模板包含“填写说明”工作表和“数据”工作表：

| 字段 | 创建必填 | 更新必填 | 类型 | 示例 | 说明 |
|---|---|---|---|---|---|
| 编码 | 否 | 否 | 文本 | `RACK-...` | 留空由后端自动生成；更新不建议改 |
| 名称 | 是 | 否/按接口 | 文本 | `02机柜` | 作为展示名称，不等于稳定身份 |
| U 位/规格 | 按对象 | 否 | 数字 | `42` | 必须为正数并满足对象规则 |
| SN | 否 | 否 | 文本 | `SN001` | 若填写需满足唯一性 |
| 管理 IP | 否 | 否 | 文本 | `192.0.2.10` | 按后端格式校验 |
| 业务 IP | 否 | 否 | 文本 | `198.51.100.10` | 可选字段 |
| 额定功耗 | 否 | 否 | 数字 | `300` | 缺失时相关利用率无法计算 |

真实字段以 OpenAPI 和前端模板工具为准；维护者不要单独修改 Excel 列名而不更新映射函数。

### 16.3 机柜图导出

机柜图导出内容：

- 机房和机柜基本信息。
- 机柜规格、U 位总数和状态。
- 按 U 位从上到下的布局。
- 设备占用区间合并显示。
- 设备信息只显示已有的字段：设备名、SN、功耗；没有 SN 或功耗就不增加空列/空文本。
- 不导出设备编号作为机柜图的展示内容，避免用户把展示列误认为唯一身份。
- 样式、颜色、边框、合并单元格和说明应保持可读且可回导。

导出格式必须稳定：导出的文件就是后续导入机柜图的模板来源。改变列名、工作表名、U 位方向或合并规则时必须更新导入兼容版本。

### 16.4 机柜图回导

回导分为两类：

#### A. 从零导入或空 U 位新增设备

- 设备没有稳定身份时视为新增候选。
- 设备编号不要求用户提供。
- 提交时后端自动生成设备编号。
- 先检查同名、同 SN、同 IP 或其他唯一属性冲突。

#### B. 原位置设备更新

- 首先根据导出时保存的稳定身份、设备 ID 或明确匹配键识别原设备。
- 原位置和设备名称未变化：保留原设备编号。
- 修改名称但其他身份仍能确定：在验证页显示“原设备改名”，由用户确认。
- 编号变化且无法确定是否原设备：必须让用户选择“原设备修改编号”或“新设备”，并给出冲突明细。
- 不能仅凭设备名称覆盖，因为名称可能重复。
- 不允许验证阶段直接更新数据库。

#### C. 删除、替换和空位

- 原导出中有设备、回导文件中变为空：列为“拟下架/移除”，要求确认。
- 原 U 位设备 A、文件中变成设备 B：列为“替换”，同时校验 A 的去向和 B 的唯一身份。
- 一个设备出现在多个位置：阻止提交。
- 同一 U 位出现重叠区间：阻止提交。
- 文件中的机柜与当前机柜版本不一致：要求重新导出或重新验证。

### 16.5 设备信息导出与回导更新

“导出设备信息”不是只读报表，而是可编辑的更新交换文件。维护此功能时：

- 导出列必须包含用于稳定匹配的不可见/受保护字段，或在说明中明确匹配键；如果产品要求用户看不到设备编号，仍应以独立的技术列、隐藏列或服务器端导出批次保存身份。
- 管理 IP、业务 IP、SN、功耗、责任人、备注等可编辑字段允许修改后再导入。
- 设备名称和编号修改必须进入冲突确认，不得默认批量覆盖。
- 空单元格的语义要明确：忽略、不修改还是清空原值，三者不可混用。
- 导入预览显示新增、更新、跳过、冲突、错误五类结果。
- 提交后返回成功数、失败数、冲突数和逐行错误信息。

### 16.6 统一 Excel 校验函数

字段映射和校验必须集中：

- 表头别名映射集中维护。
- 数字、日期、枚举、IP、SN、UUID、U 位区间校验集中维护。
- 去除首尾空格、全角半角、空行和 Excel 数字格式差异的规范化集中维护。
- 模板下载和导入解析使用同一字段定义。
- 不允许机柜导入、设备导入、机柜图回导各自复制一套字段映射。

### 16.7 Excel 安全和资源保护

- 限制上传文件大小和行数，具体阈值配置化并记录。
- 禁止将用户单元格内容直接当作公式执行。
- 导出时防止 CSV/Excel 公式注入，对以 `= + - @` 开头的用户文本做安全处理。
- 不信任文件扩展名，校验 MIME、工作簿结构和必要表头。
- 错误报告不要把完整敏感 IP、密码或 Token 回显到公开下载链接。
- 解析失败应释放临时文件和内存。

## 17. 复制与跨层级移动

### 17.1 资源复制

支持：

- 复制单个机柜。
- 复制机房及其机柜结构。
- 复制数据中心及其机房、机柜结构。

复制弹窗必须明确：目标父级、名称/编码生成方式、是否只复制结构、不会复制哪些资产。默认不复制设备、SN、资产编号、PDU 实例和设备供电连接。

### 17.2 跨机房/跨数据中心移动

移动可能是：

- 机房从数据中心 A 移到数据中心 B。
- 机柜从机房 A 移到机房 B。
- 机柜跨数据中心移动（本质上同时改变机房和数据中心归属）。

移动流程：

1. 加载源资源、目标父级和当前版本。
2. 校验目标存在、状态允许、编码作用域不冲突。
3. 评估子资源、设备活动位置、PDU 和审批影响。
4. 在事务中更新父级归属。
5. 同步设备位置的机房/数据中心字段。
6. 清空原大屏坐标和排序，目标位置由目标机房重新安排。
7. 写审计和移动履历。
8. 返回目标资源完整数据，前端刷新两棵资源树和两个大屏状态。

移动不是复制后删除，必须保留原资源 ID、设备位置和 PDU 关系，除非产品明确要求创建新资产。

### 17.3 移动失败处理

- 目标编码冲突：不改变源数据。
- 目标父级已删除或不可用：不改变源数据。
- 设备位置同步失败：整个事务回滚。
- 版本冲突：提示资源已被他人修改，要求重新加载。
- 审批开启且需审批：创建待审批记录，不直接移动。

## 18. 认证、授权、管理员与 LDAP

### 18.1 本地认证

- 密码使用 bcrypt 存储，数据库不保存明文。
- 登录成功后签发 JWT。
- 前端 Token 当前存储于 `localStorage.cabinet_access_token`。
- 服务端每次请求验证签名、过期时间、用户启用状态和角色。
- 管理员初始种子逻辑 `SeedAdmin` 只在管理员不存在时创建；修改环境变量不会自动重置已存在管理员密码。
- 忘记密码应使用管理员重置流程或受控数据库/运维流程，不能直接依赖修改 `.env`。

### 18.2 RBAC

管理员角色为 `system_admin`。`/api/v1/admin/*` 由后端 `RequireAdmin()` 保护：

- 前端不显示菜单只是体验优化，不是安全边界。
- 普通用户直接调用接口必须得到 401/403。
- 用户、角色、审批设置、LDAP 配置和连接测试均属于管理员能力。
- 修改角色后应让现有 Token 在合理时机重新校验或失效，避免权限长期滞留。

### 18.3 审批

审批设置已迁移到管理员能力：

- 普通用户不可访问策略配置。
- 上架、迁移等是否需要审批由 `operation_policies` 决定，默认关闭。
- 审批申请记录目标对象快照、申请人、申请时间、原因和版本。
- 审批人处理后写入审计。
- 不允许前端传 `approved=true` 代替管理员审批。

### 18.4 LDAP

支持真实 LDAP 服务联调。典型配置包括：

- LDAP 地址和协议。
- Base DN。
- 服务账号 DN 和 Bind 密码。
- 用户搜索基准、过滤器、用户名属性。
- 组搜索基准、组成员属性。
- LDAP 组到本地角色映射。
- 是否启用 LDAP 登录或作为本地登录的补充。

联调流程：

1. `docker compose --profile ldap up -d ldap`。
2. 按 `deploy/ldap/README.md` 创建测试目录、用户和组。
3. 在管理员页面保存 LDAP 配置，密码只提交不回显。
4. 执行连接测试，验证 Base DN 和服务账号绑定。
5. 搜索测试用户，验证用户属性映射。
6. 使用 LDAP 用户密码登录，验证本地映射记录创建/更新。
7. 将用户加入不同 LDAP 组，验证组到角色映射。
8. 移除组或停用用户，验证权限变化和登录失败行为。
9. 记录测试结果，不把测试密码提交到代码库。

LDAP 故障重点看：网络地址是否使用容器可达地址、端口是否混淆宿主映射和容器端口、Base DN 是否一致、Bind 密码是否已配置、过滤器属性是否匹配、组成员格式是否正确。

## 19. API 维护清单

完整契约以 `backend/api/openapi.yaml` 为准。维护时按领域检查以下接口类别：

### 19.1 健康和认证

- 存活检查。
- 就绪检查。
- 本地登录。
- LDAP 登录或认证入口。
- 当前用户/会话信息。

### 19.2 资源管理

- 数据中心列表、详情、创建、更新、删除、复制。
- 机房列表、详情、创建、更新、删除、复制、移动。
- 机柜列表、详情、创建、更新、删除、复制、移动。
- 房间大屏数据、布局保存、机柜状态快捷更新。

至少备份：

- PostgreSQL 逻辑备份。

- LDAP 数据卷和配置卷（如果使用 LDAP）。

## 24. 常见故障排查

### 24.1 容器退出

```bash
docker compose ps -a
docker logs --tail=300 cabinet-backend
docker logs --tail=300 cabinet-frontend
```

判断顺序：

- `Exited (1)`：优先看配置、数据库、迁移和启动 panic。
- `Exited (0)`：可能是一次性命令或被主动停止，不等于故障。
- 不断重启：检查依赖健康状态、端口占用和环境变量。
- frontend 正常而 API 失败：检查 Nginx `/api` 代理和 backend 端口。

### 24.2 后端启动失败

常见原因：

- `DATABASE_URL` 错误或 PostgreSQL 尚未 ready。
- `JWT_SECRET` 未设置或过短。
- AutoMigrate 与历史数据库结构不兼容。
- `btree_gist` 扩展权限不足。
- 端口 8080 已被占用。
- LDAP 配置格式错误（若启动时校验）。

处理：

1. 查看完整日志，不只看最后一行。
2. 用容器网络名连接依赖，不要在 backend 容器中使用宿主 `localhost`。
3. 检查 ready 接口和 PostgreSQL healthcheck。
4. 备份后再处理迁移。
5. 修复配置后只重启 backend，不要删除数据卷。

### 24.3 登录密码错误

排查顺序：

1. 确认访问的是当前部署版本，不是旧前端缓存。
2. 检查用户是否存在、是否启用、用户名是否有空格或大小写差异。
3. 区分本地账号和 LDAP 账号登录路径。
4. 查看后端认证日志（不得记录密码）。
5. 验证 bcrypt 密码校验是否成功。
6. 如果是管理员初始密码问题，确认 `SeedAdmin` 不会自动重置已存在账号。
7. 使用受控管理员重置密码接口或运维脚本。
8. 清理浏览器旧 Token 后重新登录。

### 24.4 `racksPerRow` 保存后回退

重点检查：

- 前端是否把 `0` 当成 false 并替换为 8。
- 更新请求是否根本没有提交该字段。
- Go binding 是否无法区分 omitted 和显式 0。
- service 更新白名单是否遗漏 `racks_per_row`。
- repository 是否只更新了部分字段。
- 数据库查询详情是否返回新值。
- 页面重新打开是否使用了旧 Pinia 状态覆盖服务端值。

验证必须覆盖保存 1、8、12、20，刷新页面、退出重进和不同用户读取。

### 24.5 第一个/第九个机柜显示异常

排查：

- 是否存在 `:first-child`、第 9 个特殊类或固定 8 列 CSS。
- grid/flex 子元素是否有不同 margin、transform、scale 或高度。
- 背景是否画在错误的父容器导致跨行断裂。
- 机柜卡片是否使用内容高度而非固定格位高度。
- 空机柜和有设备机柜的 U 位行高是否不一致。
- 浏览器缩放、字体加载和 scrollbar 是否改变尺寸计算。

修复原则是使用统一的机柜格位组件和 CSS 变量，动态计算行列，不以机柜序号写特殊样式。

### 24.6 点击 U 位无反应或菜单不对

- 检查事件是否绑定在空位而没有绑定在设备覆盖层。
- 检查设备层是否阻止冒泡但没有重新派发统一点击事件。
- 检查菜单数据是否用旧的正面/背面字段过滤。
- 检查目标对象是否为当前 U 区间，而不是整个机柜。
- 检查左键事件、键盘事件和触摸事件是否共用同一 action builder。
- 检查菜单动作是否携带设备 ID、机柜 ID、起始 U 和版本。

### 24.7 导入产生重复设备

- 确认导入是预览后提交，不是上传即写库。
- 确认稳定身份列没有被用户删除或改成普通名称。
- 检查空编码是否走创建生成逻辑、非空编码是否走更新匹配逻辑。
- 检查 SN、设备编号、名称和位置冲突是否分类展示。
- 检查重复提交是否使用草稿 ID/幂等键。
- 检查提交事务失败是否完整回滚。

### 24.8 LDAP 连接失败

```bash
docker compose ps ldap
docker logs --tail=300 cabinet-ldap
docker compose exec ldap ldapsearch -x -H ldap://127.0.0.1:389 \
  -D "cn=admin,dc=example,dc=org" -W \
  -b "dc=example,dc=org" -s base dn
```

常见错误：宿主端口 1389 被误填为容器内地址、Base DN 不一致、管理员密码不匹配、测试用户未导入、组属性配置错误。生产不要使用默认测试目录。

### 24.9 Excel 导入失败

- 文件是否真的是 xlsx/xls 工作簿。
- 工作表名称和必需表头是否匹配。
- 数字是否被 Excel 格式化成科学计数法。
- U 位是否为整数，起始 U 和高度是否超出机柜。
- 空值是忽略还是清空，是否符合模板说明。
- 编码为空是否允许自动生成。
- 是否超过文件大小/行数限制。
- 错误报告是否指出行号、字段、原值和修复建议。

## 25. 性能、安全与可维护性要求

### 25.1 性能

- 资源列表必须分页；大屏按机房加载，避免一次返回全系统全部 U 位。
- 设备名搜索使用后端条件和索引，不在浏览器遍历全量设备。
- 机柜详情只加载必要关联，避免 PDU、设备、履历的重复 N+1 查询。
- Excel 解析要限制大小和行数；大文件应考虑异步任务或流式处理。
- 大屏布局计算使用纯函数并缓存派生结果；拖动过程中不频繁写库，放下后一次保存。
- Redis 已从当前 Compose 配置移除。若未来重新接入，必须先有明确性能指标和缓存设计，包括键命名、TTL、失效事件、事务后失效、降级、热数据和权限隔离。

### 25.2 安全

- 所有写接口都做服务端鉴权和输入校验。
- 管理员接口必须服务端 RequireAdmin。
- 密码 bcrypt；Token 有效期和密钥安全管理。
- LDAP Bind 密码只写不读。
- SQL 使用参数化查询。
- 导入文件防止路径穿越、恶意公式和超大压缩包。
- 错误消息避免泄露数据库、文件路径、Token 和密码。
- 审计日志应记录关键操作，但对敏感字段脱敏。
- 删除、迁移、批量更新和导入提交应保留操作者、时间、对象和结果。

### 25.3 可维护性

- 领域逻辑集中到 service，避免前后端重复实现同一校验。
- 字段 schema、Excel 映射和详情渲染共享元数据。
- 使用显式 DTO，避免把数据库 model 原样暴露给所有接口。
- 为复杂操作提供幂等性或版本控制。
- 新增枚举必须更新所有消费者。
- 不保留无引用旧 CSS、旧正背面分支和历史复制代码；删除前先用全文搜索和构建确认。
- 每次修复 bug 都应增加能复现该 bug 的回归测试。

## 26. 当前技术债务与风险

### 26.1 AutoMigrate 与版本化迁移并存

当前启动流程依赖 GORM `AutoMigrate`，同时保留 SQL 迁移参考目录。短期方便，长期存在以下风险：

- 启动时隐式改表不可审计。
- 多实例同时启动可能产生迁移竞争。
- 删除列、重命名列和数据迁移无法由 AutoMigrate 安全表达。
- 回滚困难。

建议制定迁移版本表和发布前迁移流程，应用启动只执行已批准版本或只校验结构。

### 26.2 Redis 已从 Compose 中移除

当前后端没有 Redis 客户端和业务缓存调用，因此已从 Docker Compose 中移除 Redis 服务、数据卷、端口映射和 backend/go-dev 启动依赖。当前业务数据全部以 PostgreSQL 为准。若未来出现明确的缓存、分布式锁、异步任务或限流需求，应单独设计并完成测试后再接入，不得因为“预留”而恢复无业务用途的 Redis 服务。

### 26.3 历史正背面兼容字段

历史 `face` 字段可能继续存在。若数据量较大，应先统计非空值和业务依赖，再做迁移。任何“全系统取消正背面”的新代码都应防止旧字段重新渗透到唯一键、导入模板和 UI 分支。

### 26.4 Excel 同步处理风险

当前浏览器端或同步 API 处理大型工作簿可能造成内存峰值和请求超时。建议未来引入：

- 上传文件对象存储或临时文件。
- 异步解析任务。
- 进度查询。
- 过期草稿清理。
- 分批提交和结果下载。

### 26.5 大屏 DOM 和布局规模

取消资源固定上限后，大屏可能加载更多机柜和 U 位。需要监测：

- 单机房机柜数量。
- 总 U 位 DOM 数量。
- 首屏渲染时间。
- 拖动帧率。
- 搜索响应时间。
- 浏览器内存。

必要时采用虚拟滚动、分区加载、缩放层和只渲染可见行，但不能破坏固定格位和定位体验。

### 26.6 可观测性不足

建议补充：

- 请求 trace/request ID。
- 导入任务 ID 和审计关联。
- 迁移耗时、数据库错误、约束冲突计数。
- 登录成功/失败、LDAP 延迟和映射失败原因。
- 大屏加载和搜索耗时。
- 不记录敏感请求体。

### 30.1 何时必须更新本文档

出现以下任一情况必须更新：

- 修改测试门禁、构建命令或服务器验证方式。
- 发现并修复会影响维护的重大 bug。

### 30.2 更新格式

每次更新在文件顶部或发布记录中注明：

- 日期：使用具体日期，例如 `2026-09-04`。
- 版本：与项目功能基线或发布版本对应。

### 30.3 维护者快速结论

这个项目最容易再次出现问题的地方不是单个按钮，而是“同一业务被多套实现”：

1. 设备编辑表单、详情和 Excel 字段必须共享后端契约。
2. 机柜布局必须共享固定格位算法，不按序号写特殊 CSS。

6. 显式 0、空值和未提供必须严格区分。
7. 取消数量上限不能误删容量和一致性校验。
8. 正背面兼容字段不能重新成为业务维度。
9. 普通用户隐藏菜单不等于有安全保护，后端必须校验管理员。
10. 每个 bug 都要留下自动化回归测试。
